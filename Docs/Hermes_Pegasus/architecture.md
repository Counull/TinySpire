# 卡牌游戏 · 程序架构

> 杀戮尖塔 like 卡牌肉鸽的工程架构——以学习为目标的轻量技术选型。

## 当前结论

卡牌项目定位为**技术学习实验室**——用户在 MC 项目没碰过的 DI、响应式、MVVM、异步流程在这里从零摸。架构分三层：计算（纯 C#）→ 状态（R3 响应式）→ 时序（权威战斗命令队列 + UniTask 展示流程）。表现适配可以局部耦合具体 View，但共享战斗状态的修改顺序必须收口到命令队列。

## 技术选型

| 层 | 工具 | 学习目标 |
|---|---|---|
| DI | VContainer（比 Zenject 轻，Unity 原生支持） | 消除全局单例耦合 |
| 响应式 | R3（ReactiveProperty，async/await 原生支持） | buff/debuff 自动刷新 |
| MVVM | CardView ↔ CardViewModel（R3 属性绑定） | UI 不看逻辑，只看 ViewModel |
| 异步 | UniTask | 命令流程不靠协程手写 |
| 序列化 | JsonUtility / Odin / MemoryPack | Run 中断恢复——比 MC 存档简单 |
| 数据驱动 | JSON/SO 定义卡牌效果 | 何时硬编码 vs 数据驱动 |
| 测试 | NUnit（逻辑核纯 C# 不依赖 Unity） | 单元测试——MC 最缺的一块 |

## 三层架构

```
计算层（纯 C#）     → 伤害多少、buff 多久、谁死了
状态层（R3）       → 计算结果存在哪、谁关心（ReactiveProperty）
时序层（UniTask）  → 播什么动画、等多久、下一步是什么
```

**三层分开，每层只管自己那件事。**

### 权威战斗命令队列与展示

玩家输入、系统阶段事件与敌人行动都先形成战斗命令。玩家可以同时提交，提交本身不等待其他玩家输入或当前效果展示；权威调度层为已确认命令建立唯一顺序。执行器一次只处理队首命令，并等待该命令的状态修改与效果展示完成后再处理下一条：

```
玩家 A/B 同时提交
  → AuthorityOrder（建立唯一序号）
  → BattleCommandQueue
      ├─ PlayCard(A, card-12)
      │    ├─ 权威校验与状态修改
      │    └─ 顺序展示 Damage / Buff / MoveCard
      ├─ PlayCard(B, card-31)
      └─ EndPlayerAction(A)
```

提交成功与执行成功必须区分：命令排队时共享状态可能继续变化，最终合法性以队首执行时的权威状态为准。单机直接在本地分配顺序；未来联机由网络 adapter 将玩家请求转换为已确认命令，但单机和联机进入同一个执行 interface。

## 关键教训：权威顺序集中，表现适配保持局部

早期“动画队列属于过度工程”的判断建立在尚无多人同时提交和共享状态仲裁需求的前提上。该前提已由 2026-07-31 的多人命令口径替代：命令队列现在负责真实存在的权威顺序，不再只是为动画解耦而建立。

**命令排序与表现查找仍是两件事。**

| | 数据耦合（MC Map 模块） | 动画耦合（卡牌项目） |
|---|---|---|
| 后果扩散 | 网络消息或 UI 直接改共享状态会导致顺序不一致 | DamagePopup 查找具体 Transform 失败可局部跳过 |
| 传染性 | 多玩家并发写入会造成能量、卡区和触发分歧 | 单个 VFX adapter 的变化不应改变命令结果 |
| 处理方式 | 所有共享写入经权威命令顺序执行 | View 查找与动画实现保持在局部 adapter |

**核心判断线：是否会改变共享事实或命令顺序。** 会的，必须收口；只影响本地表现的，保持局部即可。

## 最小跑通目标

当前 M4 先跑通：单玩家出牌命令进入队列 → 权威校验与扣能量 → 卡区变化 → 当前命令展示完成 → 队列处理下一条。多人网络层和真实 Effect 内容后续接入同一个 interface。
