# 玩法决策记录

> 每个决策记录：选项 → 解决的问题 → 为什么选。
>
> 决策的锁定等级见 `decision-locks.md`。本文件记录“为什么这样选”，`decision-locks.md` 记录“实现时能不能顺手改”。

## 决策 001：卡牌身份模型

**问题**：一张"打击"的两个副本，是完全相同的还是独立实例？

**选项**
- 纯模板引用：所有同名牌完全一致，无升级/修改
- 实例化：template ID + 修改层，每张牌可独立变化

**选择**：实例化。

**理由**：杀戮尖塔的升级系统要求每张牌有独立状态（是否升级、被遗物/效果修改）。不做升级则不需要——但我们已选择做升级。

**程序影响**：数据架构需要 template + instance 两层。网络同步要传实例状态。

---

## 决策 002：升级时机

**问题**：升级放在什么时间窗口？

**选项**
- 篝火处（杀戮尖塔）：回血 vs 升级，二选一，瞬间决策
- 城镇阶段（横跨方尖碑）：关卡之间集体整理

**选择**：篝火处，每人独立选。

**理由**：保留路线规划的压力维度——篝火处的资源分配（生存 vs 成长）是尖塔的核心张力。联机不互相等，各选各的，队友选错也是合作体验的一部分。

---

## 决策 003：牌组循环

**问题**：抽空后自动洗牌，还是需要触发？

**选择**：自动洗牌（标准肉鸽）。

**理由**：专注 combo 构建而非弹药管理。联机环境下如果某人牌打光了干等洗牌，等待体验极差。

---

## 决策 004：手牌上限

**问题**：固定还是职业相关？

**选择**：固定（暂定 10 张，数值阶段确认）。

**理由**：不做职业差异化手牌上限。我们没有足够的设计理由让某个职业"必须扔牌"——当前阶段固定上限足够，职业的操作量差异通过费用和卡牌设计来体现，不需要另加一个手牌上限做约束。

---

## 决策 005：每回合抽牌数

**问题**：固定还是受属性影响？

**选择**：固定。

**理由**：抽牌数是一个不该给玩家压力的变量。杀戮尖塔里有遗物和卡牌能改抽牌数，但那是有意的 build 方向选择，不是被动属性绑定。现阶段固定，以后可以在遗物/卡牌层面加。

---

## 决策 006：队友手牌可见性

**问题**：能否看队友手牌？

**选择**：可见。

**理由**：联机 PVE，信息不对称没有意义。看不见手牌玩家还是会语音沟通，只是增加打字负担。

---

## 决策 007：能否送牌/交易

**问题**：能否把牌给队友？

**选择**：暂不做。留接口。

**理由**：现阶段不引入跨玩家牌组传牌——设计复杂度高，且会模糊"每个人独立的牌组构建"的核心体验。后期可以通过特定卡牌效果（"将一张手牌交给队友"）引入，但不作为默认操作。

---

## 决策 008：多人行动提交与结算顺序（2026-07-31 reopen）

**问题**：多名玩家可以同时操作时，出牌如何提交、排序、执行和展示，才能避免固定轮转与互相等待，又保持共享战斗状态确定一致？

**选项**
- 固定轮转：A→B→C→D→A→B……
- 并发提交、统一权威排序、串行结算
- 阶段性并行：拆阶段，阶段内并行
- 整回合独占（Wartales 式）：一人出完所有牌才切

**选择**：所有未结束行动的玩家可以同时向同一个战斗命令 interface 提交出牌或结束行动，不因其他玩家正在操作或前一条命令正在展示而阻塞提交。权威调度层为已确认命令建立唯一顺序，命令执行、状态修改和效果展示按该顺序一次只处理一条；不存在“一张牌后切换当前玩家”的规则。

**理由**：输入并发消除轮流等待，串行结算保证伤害、状态、触发和表现顺序确定。提交成功只表示命令进入权威排序流程，不保证执行时仍合法；最终合法性以命令到达队首时的权威状态为准。该口径参考《杀戮尖塔》的行动队列与《杀戮尖塔 2》的多人权威行动排序，但不锁定为单一物理 FIFO；未来网络实现可以使用玩家入站队列加统一仲裁，只要所有节点得到相同执行顺序。外部核验见 `../../Copilot_Daedalus/04_research/2026-07-31-slay-the-spire-action-queue.md`。

## 决策 009：超时处理

**问题**：有人卡住迟迟不出牌怎么办？

**选择**：跳过回合（暂定）。有过期时间提示，不做 AI/自动操作。可在后续阶段调整。

## 决策 010：敌人阵列模型

**问题**：四人联机，敌人是共享的还是各自独立？

**选项**
- 共享阵列：四个玩家看同一群怪，都能打同一个
- 独立阵列：每人面前自己的怪

**选择**：共享阵列为基础。机制型敌人可分血条——比如 boss 四个独立血条对应四个玩家，先打完的去帮别人。

**理由**：共享阵列支撑跨玩家 combo（破甲→上火→触发），独立阵列会让 debuff 无法跨玩家生效。分血条机制保留在 boss 战中防止四人集火秒杀。

---

## 决策 011：全项目剑盾视觉母形

**问题**：游戏中所有剑与盾相关的卡牌、意图、状态和 UI 素材如何保持统一识别？

**选择**：全项目固定两种主体母形：同一套剑/短刀作为攻击母形，同一套盾牌作为防守母形。

**理由**：主体轮廓是最稳定的识别信号。以后所有出现剑或盾的地方都复用同一套形状，不让不同素材各自重新设计剑盾，避免视觉漂移和识别成本上升。强化、衰减、格挡和特殊图标只在固定母形上改变颜色、方向、裂纹、上升/下坠纸片或组合关系。

**程序/美术影响**：卡牌插画、敌人意图、状态图标、UI 图标及后续相关素材均必须复用固定剑形或盾形；新增素材先确认属于哪一个母形，再制作状态变体。

## 决策 012：G3 地图采用尖塔式分层路线

**问题**：G3 的地图如何同时表达路线选择、保持生成和验证可控，并能稳定保存/恢复？

**选项**
- 分层 DAG：节点按层推进，边只连向下一层；允许分叉与汇合。
- 自由图：节点可任意摆放和连接，由布局算法额外保证可读性与可达性。

**选择**：分层 DAG（尖塔式路线图）。

**理由**：玩家能直接读出“我现在能去哪里”；地图生成器可纯函数化，合法性验证与存档恢复均只围绕稳定节点 ID、边和进度事实，不先引入自由图布局问题。

**程序影响**：G3-A 的 MapDefinition 是不可变地图事实；RunStateStore 只拥有当前位置、已完成与当前可选节点等可变进度。生成、合法性验证和 UI 投影分离；G3 仍只接战斗节点。**“可选节点”不得由 UI 或节点本身硬编码为“当前节点的直接出边”**，而应由独立的纯可达性规则从地图、进度和当前有效的路线修正效果计算；无修正时规则恰好等价于直接出边。未来遗物可扩展路线而不改写地图拓扑或伪造节点完成状态。

---

## 决策 013：整张地图在创建 Run 时生成并冻结

**问题**：地图是随推进逐层临时生成，还是在开局时生成完整路线？

**选项**
- 开局生成整张地图：整张图以同一份地图随机输入生成，路径信息从开局起可见。
- 渐进生成：完成一层后才生成下一层，较少需要预先保存的结构。

**选择**：创建 Run 时一次生成整张地图并冻结。

**理由**：路线规划是尖塔式地图的玩家价值；整图确定后，读档、复现、调试与验收都有同一个地图事实，不会因中断或随机调用顺序而漂移。

**程序影响**：地图随机域与 Battle、Reward 等域隔离。稳定地图态只保存可恢复地图所需的种子/生成版本/进度事实；不持久化战斗中的选中、动画或临时状态。地图层数不是硬编码常量，而是 Act 地图配置的一项**固定值**；同一份已生成地图的层数仍随 MapDefinition 冻结并保存/复现。首版不引入按 seed 抽取层数的范围语义。

## 决策 014：翼靴式跨边改道

**问题**：路线修正遗物如何改变尖塔式地图的选择，而不变成跨多层的自由传送？

**选择**：采用《杀戮尖塔》翼靴式语义：普通移动只能选当前节点的直接出边；使用路线修正效果时，可从**紧邻下一层**已生成的节点中选择目标，即使没有来自当前节点的直接连线。它不跳过地图层，也不允许回头。

**理由**：层级仍是路线节奏和内容消耗的硬约束；遗物提供的是横向改道权，让玩家重新接上原本会错失的风险、遭遇或 Boss 可达性，而非无视整张地图。

**程序影响**：可达性规则在普通模式返回直接出边；翼靴模式返回下一层节点候选，候选本身必须已存在于 MapDefinition。确认选择后，MapProgress 只记录实际选中/完成的节点，未走节点不伪造为已完成，且基础规则不支持回溯。遗物的具体使用次数、消耗时机和 UI 交互留到遗物切片 Grill。

## 决策 015：地图终点与 Boss 的多对多可达关系

**问题**：不同路线与终点 Boss 如何关联，才能既保留路线选择又不把每条路线强行锁为独占 Boss 线路？

**选择**：地图含多个 Boss 终点节点；多个终点可以映射到同一个 BossTemplate，普通路线允许分叉与汇合。Boss 是否仍可选择由当前节点所有后继终点可达的 Boss 集合决定，而不是由早期路线标签决定。

**理由**：不同路线可以因风险、奖励和节点内容而有价值，同时仍通向同一 Boss；玩家只在某个 Boss 不再位于后继路径中时才真正放弃它。

**程序影响**：MapDefinition 的终点节点保存稳定 `BossId`；可达 Boss 集合由 DAG 后继关系纯计算，不持久化为第二份状态。G3 生成、保存并展示该关系；G3 只接普通战斗节点与 Boss 门，休息、商店、事件、宝箱在后续切片接入同一套 MapDefinition / 可达性 / 结算链路，不另造路线系统；真实 Boss 战、Boss 阶段和 RunOutcome 仍属于 G7。Boss 身份在地图生成时即以明确名称和视觉锚点展示，不以问号隐藏。G3 中选中并抵达 Boss 终点会形成可保存的“Boss 门已抵达”稳定态，不伪装为普通战斗、不结算 Run；G7 在同一状态上接入实际 Boss 战。地图含不可进入的 Start 节点，作为新 Run 的稳定初始位置并连接到首层可选节点。每个节点有稳定的 `Layer` 与离散横向 `Slot`，地图视图按这两个坐标投影，不依赖自由散点/自动排版。开局展示完整地图拓扑、普通节点、连线和 Boss 终点；不可达节点仅以锁定状态投影，不能因隐藏信息改写地图事实。所有普通节点都必须从 Start 经普通直接连线可达，不生成仅能靠翼靴进入的孤儿节点；每个普通节点也必须经普通路线继续到至少一个 Boss 终点，不生成死路。每局从当前 Act 已启用 Boss 池冻结一个候选子集；每个候选 Boss 都至少有一个从 Start 经普通直接连线可达的终点，多个终点可对应同一 Boss。每张地图对应一个 Act：Start → 路线 → Boss 门 → Boss 战构成该 Act；未来 Boss 胜利后才生成下一 Act 的新地图。普通战斗节点也在地图生成时冻结稳定 `EncounterId`，进战只读取该事实，不在进入节点或读档后重抽；地图以遭遇名称与主敌人头像/剪影明牌其身份，但不提前展开行动表、血量和数值。玩家悬停或选中当前可选节点时，地图高亮该节点仍可抵达的 Boss 终点，并弱化将被放弃的 Boss 路线；同时高亮该节点全部后继可达节点与连线，作为完整的后半程路线预览。

## 决策 016：普通战斗失败立即终结 Run

**问题**：在真实多节点地图中，普通战斗失败是允许同节点重试，还是结束本局？

**选择**：失败立即终结当前 Run，不允许通过地图稳定态重试同一节点。

**理由**：路线选择、生命管理和风险评估必须承担失败后果；G1 的失败快照重试仅是单节点流程切片的临时脚手架，不是 roguelike 外层循环的目标规则。

**程序影响**：G3 计划必须显式替换既有失败重试链，不可把 `RunBattleSnapshot` 继承为地图能力。失败不得修改地图为“完成”；它产生类型化终局事实，并将 active save 原子替换为 `Terminal(Defeat)` 终局档，永久禁用 Continue。失败页确认离开后才删除终局档；若此前退出或崩溃，冷启动直接恢复失败页，仍不可继续 Run。其余终局/删除顺序仍需单独 Grill。该决定与当前 `RUN_ROADMAP.md` 的 G3 失败重试描述冲突，待本轮 Grill 收敛后作为 Roadmap 变更请求交给 Daedalus，而非在此静默改写实现路线。
